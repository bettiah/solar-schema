## Envelope (ISA/IEA)

- ISA: exactly 106 chars, fixed-length fields, defines delimiters
- ISA16: component separator (composites) - usually `:` `>` `^`
- Element delimiter after ISA (pos 104) - usually `*`
- Segment terminator (pos 106) - usually `~`
- IEA: count of functional groups
- `^` | **Repetition Separator** | Allows a specific element to repeat. (Less common but important).

| ISA Element | Name | Example Value | Mandatory? | Description |
|:------------| :--- | :--- | :--- | :--- |
| **ISA01**   | Authorization Information Qualifier | `00` | M | Specifies the type of authorization information present in ISA02. `00` means "No Authorization Information Present," which is almost always the case today. |
| **ISA02**   | Authorization Information | `          ` | M | A 10-character field for authorization data (like a password). Almost always filled with 10 spaces. |
| **ISA03**   | Security Information Qualifier | `00` | M | Specifies the type of security information in ISA04. `00` means "No Security Information Present." Security is now handled by the communication protocol (like AS2, SFTP), not in the EDI data. |
| **ISA04**   | Security Information | `          ` | M | A 10-character field for security data. Almost always filled with 10 spaces. |
| **ISA05**   | Interchange ID Qualifier | `ZZ` | M | Defines the type of ID used for the sender and receiver. **Common values:** `01` (D-U-N-S Number), `12` (Phone Number), `ZZ` (Mutually Defined). `ZZ` is very common. |
| **ISA06**   | Interchange Sender ID | `SENDERID       ` | M | The unique ID of the company sending the file. It's a 15-character field. If the ID is shorter, it **must be padded with spaces** on the right. This ID must match exactly what the trading partner expects. |
| **ISA07**   | Interchange ID Qualifier | `ZZ` | M | Same as ISA05, but for the receiver. |
| **ISA08**   | Interchange Receiver ID | `RECEIVERID     ` | M | The unique ID of the company receiving the file. It's a 15-character field and must also be padded with spaces if shorter. |
| **ISA09**   | Interchange Date | `231027` | M | The date the transmission was created in **YYMMDD** format. (Example: October 27, 2023) |
| **ISA10**   | Interchange Time | `1130` | M | The time the transmission was created in **HHMM** format (24-hour clock). (Example: 11:30 AM) |
| **ISA11**   | Repetition Separator / Interchange Control Standards ID | `U` | M | This element has been redefined over time. In modern versions (like 4010+), it is the **Interchange Control Standards Identifier**. `U` means it conforms to U.S. EDI Community of ASC X12 standards. *In older versions, this was the repetition separator.* |
| **ISA12**   | Interchange Control Version Number | `00401` | M | Specifies the version of the X12 standard being used. `00401` and `00501` are very common. This tells the receiving system which "dictionary" to use to interpret the file. |
| **ISA13**   | Interchange Control Number | `000000123` | M | A unique 9-digit number that identifies this specific interchange. This number **must match the number in IEA02**. It's crucial for tracking and acknowledging receipt. It should never be duplicated for the same sender-receiver pair. |
| **ISA14**   | Acknowledgment Requested | `1` | M | A flag indicating if the sender wants a technical receipt (a 997 Functional Acknowledgment). `1` = Yes, please send a 997. `0` = No, I don't need one. |
| **ISA15**   | Usage Indicator | `P` | M | Indicates if the data is for a real business transaction or just a test. **`P` = Production**, **`T` = Test**. This is critical; sending test data to a production system can cause major problems. |
| **ISA16**   | Component Element Separator | `:` | M | **This defines the delimiter** that will be used to separate sub-elements within a composite data element for the *entire file*. The `*` (element separator) and `~` (segment terminator) are defined by their position, but this one is explicitly stated here. Common values are `:` or `>`. |

## Inner Envelope: Functional Group

- Logical Grouping: They bundle transaction sets of the same type. For example, all invoices (810) going to the same receiver would be in one functional group with code "IN".
- Routing Information: The GS segment contains sender/receiver application codes, allowing the receiving system to route the contained transactions to the appropriate processing application.
- Version Control: The GS segment specifies which X12 version (e.g., "005010") applies to all transaction sets within that group. 
- Acknowledgment Scope: When you send a 997 Functional Acknowledgment, it acknowledges an entire functional group, not individual transaction sets.
- Control and Auditing: Like the Interchange, the Functional Group has its own control numbers and counts, providing another layer of validation to ensure all documents within the group were received correctly.


| Element | Name | Example Value | Mandatory? | Description |
| :--- | :--- | :--- | :--- | :--- |
| **GS01** | Functional Identifier Code | `PO` | M | A 2-character code that identifies the type of transaction sets within this group. **This is the key to grouping.** Common codes: `PO` (Purchase Order - 850), `IN` (Invoice - 810), `SH` (Ship Notice - 856), `FA` (Functional Acknowledgment - 997). |
| **GS02** | Application Sender's Code | `SENDERAPP` | M | The ID of the application or department sending the data. This is often more specific than the company ID in `ISA06`. |
| **GS03** | Application Receiver's Code | `RECEIVERAPP` | M | The ID of the application or department that should receive the data. This helps with internal routing on the partner's side. |
| **GS04** | Date | `20231027` | M | The date the group was created in **CCYYMMDD** format. Note the 4-digit year, which is different from the `ISA` segment's YYMMDD. |
| **GS05** | Time | `1130` | M | The time the group was created in **HHMM** format (24-hour clock). |
| **GS06** | Group Control Number | `123` | M | A unique number assigned by the sender to identify this functional group. This number **must match the number in GE02**. It's typically a sequence that increments for each new group sent to that partner. |
| **GS07** | Responsible Agency Code | `X` | M | A code identifying the standards body. `X` is used for ASC X12. |
| **GS08** | Version / Release / Industry ID Code | `004010` | M | Specifies the version of the transaction set implementation guides used for all documents in this group (e.g., `004010` for version 4010, `005010` for 5010). This should be compatible with the overall version in `ISA12`. |

How They Tie to Transaction Sets - Looking at sethead.txt:
```
"810","Invoice","IN"
"850","Purchase Order","PO"
"856","Ship Notice/Manifest","SH"
```
The third field is the Functional Group ID. This creates a binding:

Transaction Set 810 → Functional Group "IN" (Invoice)
Transaction Set 850 → Functional Group "PO" (Purchase Order)
Transaction Set 856 → Functional Group "SH" (Ship Notice)

Practical Example - If you're sending 5 invoices and 3 purchase orders to a trading partner, you'd structure it as:

```
ISA... (interchange start)
  GS*IN*... (start invoice group)
    ST*810*0001 (invoice 1)
    SE*...
    ST*810*0002 (invoice 2)
    SE*...
    ... (invoices 3-5)
  GE*5*... (end group, 5 transaction sets)
  GS*PO*... (start purchase order group)
    ST*850*0001 (PO 1)
    SE*...
    ... (POs 2-3)
  GE*3*... (end group, 3 transaction sets)
IEA*2*... (interchange end, 2 functional groups)
```

The Constraint - A functional group can only contain transaction sets that belong to that group. You cannot put an 810 (Invoice) inside a "PO" functional group - the functional group ID in sethead.txt defines which group each transaction set type belongs to.

This is why FUNCTIONAL_GROUP_CODES in the enums maps codes to descriptions - it's the master list of valid group identifiers, and each transaction set is assigned to exactly one of them.

Groups same-type transaction sets for routing & acknowledgment.

- GS01: Functional Group ID (IN=invoice, PO=purchase order)
- GS08: Version (005010X222)
- 997/999 acknowledges at this level
- Cannot mix transaction types in one group

## Transaction Set (ST/SE)

- ST01: 3-digit ID (810=Invoice, 850=PO, 856=ASN)
- ST02: control # (unique in group)
- SE01: segment count (incl ST/SE)
- 300+ types, structure in setdetl.txt
- Areas: 1=Heading, 2=Detail, 3=Summary

## Loops

Repeated segment groups, can nest. There are **three distinct types** of loops in X12 documents.

### 1. Syntactic/Bounded Loops (LS/LE Delimited)

These are **explicitly marked in the document** using `LS` (Loop Start) and `LE` (Loop End) segments with a loop identifier.

**Example from 124 Vehicle Service (4010 setdetl.txt):**
```
"124","2","280","LS","O","1","2","0",""      ← Loop Start marker
"124","2","290","NM1","O","1","3",">1","3310"
"124","2","300","N2","O","2","3","0",""
...
"124","2","370","LE","O","1","2","0",""      ← Loop End marker
```

**In the actual EDI document:**
```
LS*3310~           ← Start of loop 3310
  NM1*ST*1*SMITH~
  N2*EXTRA NAME~
  N3*123 MAIN ST~
LE*3310~           ← End of loop 3310
```

**Key point:** A parser can identify these loops **without a schema** because the delimiters are syntactically present in the document.

---

### 2. Schema-Based/Unbounded Loops (Implicit)

These have **NO explicit delimiters** in the document. The loop boundaries exist only in the schema definition.

**Example from 850 Purchase Order (4010 setdetl.txt):**
```
setdetl.txt format: TxnSet, Area, Seq, SegID, Req, MaxRepeat, LoopLevel, MaxLoopIter, LoopID

"850","1","310","N1","O","1","1","200","N1"   ← Loop trigger (level 1, up to 200 iterations)
"850","1","320","N2","O","2","1","0",""       ← Part of N1 loop (level 1, not a trigger)
"850","1","330","N3","O","2","1","0",""       ← Part of N1 loop
"850","1","340","N4","O",">1","1","0",""      ← Part of N1 loop
"850","1","350","REF","O","12","1","0",""     ← Part of N1 loop
```

**In the actual EDI document:**
```
N1*ST*ACME WAREHOUSE~      ← First N1 loop iteration
N3*123 SHIPPING LANE~
N4*CHICAGO*IL*60601~
N1*BT*BILLING DEPT~        ← Second N1 loop iteration
N3*456 BILLING AVE~
N4*NEW YORK*NY*10001~
PO1*001*10*EA*19.95~       ← Next segment type - loop ended implicitly
```

Notice: **There is NO "end of loop" marker.** The loop ends when:
- A segment appears that belongs to a different loop
- A segment at a lower loop level (parent level) appears
- The transaction set ends

---

### 3. HL Hierarchical Loops (Runtime Dynamic)

These are a **special hybrid** used in documents like 856 ASN, 837 Healthcare Claim, 270/271 Eligibility.

**From 856 ASN (4010 setdetl.txt):**
```
"856","2","010","HL","M","1","1","200000","HL"
```

The HL segment itself contains the hierarchy information:

```
HL*1**S~              ← Shipment level (ID=1, no parent, code=S)
TD5*B*2*FEDX~
HL*2*1*O~             ← Order level (ID=2, parent=1, code=O)
PRF*PO-12345~
HL*3*2*P~             ← Pack level (ID=3, parent=2, code=P)
MAN*GM*00123456789~
HL*4*3*I~             ← Item level (ID=4, parent=3, code=I)
LIN**UP*888777666~
```

The hierarchy is **defined at runtime** by the data itself (HL01=ID, HL02=parent ID, HL03=level code), not by schema structure.

---

### Why Schemas Are Required for Unbounded Loops

Consider this raw EDI fragment:
```
N1*ST*WAREHOUSE A~
N3*100 MAIN ST~
N4*CHICAGO*IL*60601~
N1*BT*BILLING DEPT~
N3*200 BILLING RD~
REF*PO*12345~
PO1*001*10*EA*19.95~
```

**Without a schema, a parser cannot answer:**

1. **Which segments belong to which loop?**
   - Does `REF*PO*12345~` belong to the second N1 loop, or is it a header-level segment?
   - The schema tells us: `REF` at loop level 1 under N1 → it's part of the N1 loop

2. **When does a loop iteration end?**
   - Does seeing a second `N1` mean we're starting a new iteration of the same loop, or starting a different loop?
   - The schema defines that N1 at position 310 with loop ID "N1" allows up to 200 iterations

3. **What is the nesting relationship?**
   - Looking at 850's detail area:
   ```
   "850","2","010","PO1","M","1","1","100000","PO1"  ← Level 1 loop
   "850","2","350","N1","O","1","2","200","N1"       ← Level 2 loop (nested under PO1)
   ```
   - The `N1` in detail area (level 2) is nested under `PO1` (level 1), NOT the same as the header N1

4. **Loop cardinality validation:**
   - How many times can a loop repeat?
   - 850 header N1: max 200 iterations
   - 850 detail PO1: max 100,000 iterations

**The schema provides:**
- Loop trigger segments (which segment ID starts a loop)
- Loop nesting levels (0=no loop, 1=top-level, 2=nested, etc.)
- Max iterations per loop
- Which segments are members of which loops

---

### Loop Type Summary

| Loop Type | Delimited By | Schema Required to Parse? | Example |
|-----------|--------------|---------------------------|---------|
| **Bounded (LS/LE)** | Explicit `LS`/`LE` segments | No - syntactically visible | 124, 175, 186 |
| **Unbounded (Implicit)** | Schema-defined triggers | **Yes** - no visible boundaries | 850 N1, PO1 loops |
| **HL Hierarchy** | `HL` segment parent references | Partial - hierarchy is in data, but segment grouping needs schema | 856, 837, 270/271 |

The schema files (`setdetl.txt`) encode loop structure in columns 7-9:
- **Column 7 (Loop Level):** 0=not in loop, 1=first level, 2=nested under level 1, etc.
- **Column 8 (Max Loop Iterations):** `>1` = unlimited, `0` = not a loop trigger, number = max count
- **Column 9 (Loop ID):** Identifies which loop this segment triggers or belongs to

## 997 Functional Acknowledgment

### AK Segment Hierarchy

The segments are structured in a logical loop that mirrors the structure of the file being acknowledged. This hierarchy is essential for pinpointing errors.

Here is the hierarchy, visualized:

`AK1` - Acknowledges the Functional Group (`GS`/`GE`)
   |
   `--> AK2` - Acknowledges a Transaction Set (`ST`/`SE`) within that group. **(This segment can loop for multiple transactions)**
       |
       `--> AK3` - Identifies a segment in error *within the AK2 transaction*. **(Optional Loop)**
           |
           `--> AK4` - Details the specific data element in error *within the AK3 segment*. **(Optional Loop)**
       |
       `--> AK5` - Provides the overall status (e.g., Accepted/Rejected) for the *AK2 transaction*.

`AK9` - Provides the summary status for the entire `AK1` Functional Group.

As you can see, `AK3`, `AK4`, and `AK5` are all "children" of `AK2` because they report on the specific transaction that `AK2` identified.

---

### Deep Dive into Each AK Segment

Let's examine each one's purpose and elements.

#### `AK1` - Functional Group Response Header
*   **Purpose:** To identify the Functional Group (`GS` segment) from the original file that is being acknowledged.
*   **Example:** `AK1*PO*555~`
*   **Breakdown:**
    *   `AK101`: `PO` - The Functional Identifier Code from the original `GS01`.
    *   `AK102`: `555` - The Group Control Number from the original `GS06`.
*   **Plain English:** "I am now reporting on the Functional Group for Purchase Orders (`PO`) that you labeled with control number `555`."

#### `AK2` - Transaction Set Response Header
*   **Purpose:** To identify a specific Transaction Set (`ST` segment) inside the group that is being acknowledged.
*   **Example:** `AK2*850*0001~`
*   **Breakdown:**
    *   `AK201`: `850` - The Transaction Set ID Code from the original `ST01`.
    *   `AK202`: `0001` - The Transaction Set Control Number from the original `ST02`.
*   **Plain English:** "Within that group, I am now reporting on the Purchase Order (`850`) that you labeled with control number `0001`."

#### `AK3` - Data Segment Note
*   **Purpose:** To pinpoint the exact **segment** that contains an error. **This segment only appears if there is an error.**
*   **Example:** `AK3*DTM*5**8~`
*   **Breakdown:**
    *   `AK301`: `DTM` - The segment ID of the segment in error.
    *   `AK302`: `5` - The position of that segment within the transaction set (it was the 5th segment after `ST`).
    *   `AK304`: `8` - An error code, e.g., '8' means "Segment Not in Defined Transaction Set".
*   **Plain English:** "I found an error in the `DTM` segment, which was the 5th segment in the 850."

#### `AK4` - Data Element Note
*   **Purpose:** To pinpoint the exact **data element** (field) that is wrong and provide the bad data. It's always a child of an `AK3`. **This segment only appears if there is a data-level error.**
*   **Example:** `AK4*02*7*6*XYZ~`
*   **Breakdown:**
    *   `AK401`: `02` - The position of the element in error (e.g., `DTM02`). Can also be a composite position like `2:1`.
    *   `AK402`: `7` - The Data Element Reference Number from the X12 standard (optional).
    *   `AK403`: `6` - An error code, e.g., '6' means "Invalid Character in Data Element".
    *   `AK404`: `XYZ` - A copy of the bad data that was found in the element.
*   **Plain English:** "Specifically, the error in the `DTM` segment was in its 2nd element (`DTM02`). The data `XYZ` contained an invalid character."

#### `AK5` - Transaction Set Response Trailer
*   **Purpose:** To provide the final "verdict" for the Transaction Set identified by the parent `AK2`.
*   **Example:** `AK5*R*5~`
*   **Breakdown:**
    *   `AK501`: `R` - The Transaction Set Acknowledgment Code. This is the most important part!
        *   `A` = Accepted
        *   `E` = Accepted But Errors Were Noted
        *   `R` = Rejected
    *   `AK502`-`AK506`: Codes for up to five syntax errors found in this transaction set. `5` might mean "Segment Not in Proper Sequence".
*   **Plain English:** "Because of the errors I noted, I have **Rejected** (`R`) the entire 850 with control number `0001`."

#### `AK9` - Functional Group Response Trailer
*   **Purpose:** To provide the final "verdict" for the entire Functional Group identified by the parent `AK1`.
*   **Example:** `AK9*R*1*1*0~`
*   **Breakdown:**
    *   `AK901`: `R` - The Functional Group Acknowledgment Code (`A`, `E`, `R`, `P` for Partially Accepted).
    *   `AK902`: `1` - The number of transaction sets received in the group.
    *   `AK903`: `1` - The number of transaction sets included in this acknowledgment.
    *   `AK904`: `0` - The number of transaction sets **accepted** in the group.
*   **Plain English:** "My final summary for the entire group `555` is that it is **Rejected** (`R`). I received 1 transaction set, and I accepted 0 of them."

---

### Putting it Together: The "Rejected" Scenario

This example shows the full hierarchy in action.

```edi
AK1*PO*555~          // Acknowledging PO Group #555
   |
   `--> AK2*850*0001~       // Acknowledging 850 #0001 within that group
       |
       `--> AK3*BEG*3**5~   // ERROR LOCATION: The BEG segment (3rd segment) is not in the proper sequence.
       |
       `--> AK5*R*5~       // VERDICT for 850 #0001: REJECTED, due to error code 5 (Improper Sequence).
|
AK9*R*1*1*0~          // FINAL VERDICT for Group #555: REJECTED. (Received 1, Accepted 0).
```

This structure allows an automated system to parse the 997, immediately know which 850 failed (`AK2*850*0001~`), why it failed (`AK5*R*5~`), and exactly where the error was (`AK3*BEG*3...~`), so it can be flagged for correction.

## 856 ASN

*   **WHAT** is in the shipment (which products).
*   **HOW MUCH** of each product is coming.
*   **HOW** it is all packaged (which items are in which boxes, and which boxes are on which pallets).
*   **WHEN** it will arrive.
*   **TRACKING** information for the carrier.

---

### The Engine of the Hierarchy: The `HL` Segment

The entire structure of an 856 is built using the `HL` segment. It's like a special bookmark or a divider in a binder that creates sections and sub-sections. Each `HL` segment marks the beginning of a new level in the hierarchy.

Let's break down the `HL` segment itself:

`HL * Hierarchical ID Number * Hierarchical Parent ID Number * Hierarchical Level Code ~`

*   `HL*1**S~`
*   `HL*2*1*O~`
*   `HL*3*2*P~`

**The Three Critical Elements:**

1.  **HL01 - Hierarchical ID Number:** A unique, sequential number for each `HL` segment in the transaction (1, 2, 3, 4...). This is the ID of the *current* level.
2.  **HL02 - Hierarchical Parent ID Number:** The ID number (`HL01`) of the level directly above this one. This is the **magic link** that creates the parent-child relationship. The very first `HL` (the Shipment level) has no parent, so this is left empty.
3.  **HL03 - Hierarchical Level Code:** A one or two-letter code that defines what this level represents.

---

### The SOPI Structure: Building the Digital Pallet

SOPI is the most common way to organize an ASN. It mirrors how goods are physically picked, packed, and shipped.

Here are the standard `HL03` codes for the SOPI hierarchy:

| Code | Level | Analogy | Description |
| :--- | :--- | :--- | :--- |
| **S** | **Shipment** | The entire truckload or delivery | The top-most level. Contains information about the entire shipment, like carrier details, ship-to address, and total weight. |
| **O** | **Order** | A customer's purchase order | Nested under the Shipment. Identifies the specific Purchase Order (`PRF` segment) that this part of the shipment is fulfilling. |
| **P** | **Pack / Pallet** | A single physical carton or pallet | Nested under the Order. This is the physical container. It is typically identified by a unique SSCC-18 barcode (`MAN` segment). |
| **I** | **Item** | An actual product inside the carton | Nested under the Pack. This is the actual item being shipped, identified by its UPC or SKU (`LIN` segment), with the quantity shipped (`SN1` segment). |

### Visualizing the Hierarchy

```
HL (S) - Shipment Level (The entire truckload)
 |
 +--> HL (O) - Order Level (Fulfilling PO #123)
      |
      +--> HL (P) - Pack Level (Carton #1 with SSCC barcode)
      |    |
      |    +--> HL (I) - Item Level (10 units of Product A)
      |    |
      |    +--> HL (I) - Item Level (5 units of Product B)
      |
      +--> HL (P) - Pack Level (Carton #2 with SSCC barcode)

```

### Putting It All Together: A Simplified 856 ASN Example

Let's trace a simple shipment:
*   **Shipment:** One shipment going to a distribution center.
*   **Order:** Fulfilling one Purchase Order, `PO-98765`.
*   **Packs:** Two separate cartons.
    *   Carton 1 contains 10 of Item A.
    *   Carton 2 contains 25 of Item B.

```edi
ST*856*0001~
BSN*00*SHIPMENT123*20231027*1430~  // Beginning Segment for Ship Notice

// --- SHIPMENT LEVEL ---
HL*1**S~                          // HL #1, No Parent, this is the Shipment level.
TD5*B*2*FEDX*M~                   // Carrier Details: FedEx Ground
N1*ST*WAREHOUSE DC 123~           // Ship To: The destination warehouse
N1*SH*ACME WIDGETS INC~           // Ship From: The sender

// --- ORDER LEVEL ---
HL*2*1*O~                         // HL #2, Parent is HL #1, this is an Order level.
PRF*PO-98765~                     // Purchase Order Reference: This fulfills PO-98765.
```
